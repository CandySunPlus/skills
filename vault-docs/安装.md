# 把镜像机制装到一个新仓库

装完你会得到：Obsidian 里的一批文档单向同步到仓库、仓库内改动被三道防线拦住、
以及一条不需要访问 vault 就能跑的校验（所以 CI 也能跑）。

## 一、放脚本

`scripts/` 下四个文件整组复制到目标仓库，四个要放在同一个目录里：

```
scripts/mirror-common.sh       # 读配置、算路径、算哈希，另两个脚本 source 它
scripts/sync-docs.sh           # vault → 仓库
scripts/check-docs-mirror.sh   # 校验，不碰 vault
scripts/rewrite_wikilinks.py   # [[wikilink]] → 相对链接
```

**目录必须是仓库根的一级子目录**（`scripts/`、`tools/` 都行，`build/bin/` 不行）：
脚本按 `脚本目录/..` 认仓库根。放深一层的后果是它把子目录当成仓库根，然后往
错的地方找 `.mirror.conf`。

四个都给上可执行位（`chmod +x scripts/*.sh scripts/rewrite_wikilinks.py`）。`mirror-common.sh`
是被 source 的，给了也无害，省得记哪个要哪个不要。

`MIRROR_DEST` 的父目录不用先建——`sync-docs.sh` 会 `mkdir -p`。

## 二、写配置

配置分两份，按「谁的值」分：仓库侧的入 Git，本机的不入。

**`.mirror.conf`** —— `templates/mirror.conf` 复制到**仓库根**，命名 `.mirror.conf`，入 Git。
里面每一项都是全项目一致的值，决定哪些文件算镜像内容：

| 键 | 改成什么 |
|---|---|
| `MIRROR_DEST` | 镜像装哪，相对仓库根。这个目录归 `rsync --delete` 全权管理，不要往里放别的东西 |
| `MIRROR_VAULT_SUBPATH` | vault 里哪个子目录是源；整个 vault 都要就留空 |
| `MIRROR_TYPES` | 进镜像的扩展名。**只写真的要的**——多收一类就多一类「vault 里删了、镜像跟着被清掉」的东西 |
| `MIRROR_EXCLUDES` | 要排除的路径。vault 侧指回本仓库的软链**一定**要列，否则哪天 rsync 加了 `-L` 会把仓库自己抄进镜像 |

**`.mirror.conf.local`** —— `templates/mirror.conf.local` 复制到仓库根，`MIRROR_VAULT_ROOT`
改成你这台机器上的 vault 根目录。**不入 Git**（`.gitignore` 见第四节），每人一份。

vault 位置单独一份，因为它是一条本机绝对路径、每台机器不同，而每人不同的值一旦进了
共享文件，那一行就永远处在「本地改了但不能提交」的状态。

`check-docs-mirror.sh` 与 CI 只读 `.mirror.conf`：它们要知道镜像装在哪，但从不访问
vault——CI 上也根本没有 vault。

本机文件里只许有 `MIRROR_VAULT_ROOT` 与 `MIRROR_VAULT_DOCS`。写别的键会被
`mirror-common.sh` 当场拒掉：本机覆盖了 `MIRROR_DEST` 之类，本机同步产出的镜像与 CI
读的那份配置就不是一回事，症状是校验报一堆「多出文件 / 文件缺失」，而根因藏在一个
不入 Git 的文件里。

临时指向另一个 vault 不必动配置，同名环境变量优先级最高：

```bash
MIRROR_VAULT_ROOT=/别的/vault ./scripts/sync-docs.sh
```

## 三、横幅

`templates/mirror-banner.md` 复制到 `MIRROR_BANNER` 指的位置，改文案。

**不要放在 `MIRROR_DEST` 里面**——那儿每次同步都会被 `--delete` 清掉。放它的兄弟
位置（比如镜像在 `docs/需求/`，横幅放 `docs/.mirror-banner.md`）。

**模板里那条链接的目标要按你仓库的实际位置改。** `{{UP}}` 替换成「从当前文件回到
镜像父目录」的相对前缀，所以 `]({{UP}}README.md)` 指的是**镜像父目录下的
README.md**——模板发的是这个默认值，因为它来自一个说明文档正好在那儿的仓库。

以镜像装在 `docs/笔记/` 为例：

| 文件 | `{{UP}}` 展开成 | `{{UP}}README.md` 指向 |
|---|---|---|
| `docs/笔记/00-索引.md` | `../` | `docs/README.md` |
| `docs/笔记/子目录/02-细节.md` | `../../` | `docs/README.md` |

说明文档在仓库根（`./README.md`）的话，写 `]({{UP}}../README.md)`。

指错了 `sync-docs.sh` 会当场报错并中止——这条不能靠人眼盯：横幅里的死链是基线的
一部分，三道防线全绿。

横幅文案里不要出现机器相关的路径：它进基线，各机器同步结果必须一致。

## 四、忽略项

`.gitignore` 补两条：

```gitignore
# vault 在本机的哪儿，每人一份
.mirror.conf.local
# 只读镜像被就地改过时，sync-docs.sh 留下的手改备份
docs/.笔记-手改备份-*/
```

第二条的 pattern 是 `<镜像父目录>/.<镜像目录名>-手改备份-*/`，上面按镜像装在
`docs/笔记/` 写。两条漏了的症状都是那东西哪天悄悄进 Git。

## 五、三道防线

单靠"README 里写了别改"拦不住，尤其协作者根本不知道这是镜像。

**提示层** —— `templates/gitattributes.snippet` 追加到 `.gitattributes`，把
`MIRROR_DEST` 换成实际值。GitHub 的 PR diff 会默认折叠这些文件。

**提交前** —— `templates/pre-commit` 复制到 `.githooks/pre-commit`，`chmod +x`，然后
每人每个克隆执行一次：

```bash
git config core.hooksPath .githooks
```

**CI** —— `templates/docs-mirror.yml` 复制到 `.github/workflows/`，把里面所有
`MIRROR_DEST` 占位符换成实际值，替换完把顶部那段安装说明删掉（Actions 的 `paths`
读不了配置文件，只能手工对齐）。替换完 `rg -c MIRROR_DEST` 应该没有命中。
PR 上显示的检查名取自 job 名 `verify`，不是文件顶部的 `name`。

## 六、首次同步

```bash
./scripts/sync-docs.sh
./scripts/check-docs-mirror.sh
```

镜像与基线一起提交。基线漏提交的症状是别人和 CI 报「内容被修改」。

## 七、证明这条检查会失败

不会失败的检查比没有检查更糟：它稳定地报告成功，还让人以为查过了。所以装完立刻
往镜像里塞一个明显的违规，确认非零退出，再还原：

```bash
echo x >> <镜像里任意一个 .md>
./scripts/check-docs-mirror.sh; echo "退出码=$?"      # 必须非 0，且列出那个文件
git checkout -- <镜像目录> <基线文件>
./scripts/check-docs-mirror.sh; echo "退出码=$?"      # 回到 0
```

再验一次 hook 真的挂上了（`core.hooksPath` 配错时它会安静地什么都不做）：

```bash
echo x >> <镜像里任意一个 .md>
git add -A && git commit -m 试 ; echo "退出码=$?"     # 必须非 0，提交被拦下
git reset -q -- <镜像目录> <基线文件>                  # 先退出暂存区
git checkout -- <镜像目录> <基线文件>
git status --short                                    # 必须无输出
```

**`git reset` 这一步不能省。** 探针里那个 `+x` 已经进了暂存区，而 `git checkout --`
只动工作区、不撤暂存。少跑这一步，那处违规会一直 staged 着，被下一个提交顺手带走——
而它一旦进了提交，CI 那道防线才会拦下来，这时候你已经在排查一个跟当前改动无关的红。

## 多人协作

**这套机制只有一个源。** 「把镜像同步进我自己的 vault」是在造第二个源，而两个源
配上 `rsync --delete` 会互删：两个人各指自己的 vault、都跑 `sync-docs.sh`，谁后跑谁
把对方那批文件从镜像里清掉。这种删除三条校验一律全绿（基线由同一次同步重写），唯一
露头的地方是 `sync-docs.sh` 末尾那个 `git status --short` 里的 `D`。所以走下面三条路
里的一条，不要各自复制一份 vault。

**多人都要改文档 → 共享 vault 本身。** Obsidian Sync、把 vault 自己做成一个 git 仓库、
或者放云盘。每人的 `.mirror.conf.local` 指向本机那份的位置，`sync-docs.sh` 谁跑都一样。
各人 vault 布局不同时（共享的只是其中一部分），用本机文件里的 `MIRROR_VAULT_DOCS`
直接给出源目录的完整路径，绕过全项目共用的 `MIRROR_VAULT_SUBPATH`。

**只是要在 Obsidian 里读 → 把仓库的镜像目录当成一个 vault 打开**，不要复制。
`[[wikilink]]` 已被改写成相对链接，Obsidian 也跟得动。它是只读的：在那儿改会被
pre-commit 拒，而没装 hook 时会一路进 PR。

**共享不了 vault → 单一文档 owner。** 其他人直接读仓库里的镜像（内容与 vault 逐字
一致，只多了顶部横幅），意见提在 PR 或 issue 里，owner 在 vault 里落。注意 `==高亮==`
加脚注那套就地批注需要 vault 的写权限，所以它只对共享 vault 的人可用。

## 它查不出什么

**vault 里删掉或漏掉的文件。** 基线由同一次同步重写，所以那种缺失对
`check-docs-mirror.sh` 和 `shasum -c` 都不可见——两者全绿，而镜像里的文件已经被
`rsync --delete` 清掉了。唯一露头的地方是 `sync-docs.sh` 末尾打的
`git status --short`：**出现 `D` 就停下来确认那是有意的**，别顺手连着提交。

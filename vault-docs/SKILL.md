# vault-docs

让 Obsidian vault 当文档的唯一编辑入口、仓库里只放**只读镜像**的一套机制，外加走这条路时几个**校验查不出来**的坑。

- 装到新仓库：`安装.md`
- 已装好的仓库跟上 skill 的当前版本：`升级.md`（脚本是复制进去的，不会自己跟上）
- 脚本：`scripts/`（四个文件一组，装在仓库根的一级子目录下）
- 模板：`templates/`（配置、横幅、hook、CI、gitattributes）

## 机制的形状

| 件 | 管什么 |
|---|---|
| `sync-docs.sh` | vault → 仓库单向同步（`rsync --delete`）、注入只读横幅、检测并备份手改、改写 wikilink、写基线 |
| `check-docs-mirror.sh` | 校验镜像与基线一致。**不碰 vault**，所以 CI 也能跑 |
| `<镜像>.manifest` | 基线，每个文件的 sha256，随仓库提交 |
| `.mirror.conf` | 仓库侧取值，入 Git：镜像装哪、vault 的哪个子目录是源、收哪些扩展名、排除什么、横幅模板 |
| `.mirror.conf.local` | 本机取值，不入 Git：`MIRROR_VAULT_ROOT`（vault 在这台机器的哪儿）。CI 里没有也不需要 |

基线是这套机制的关键：**光比对内容分不清「vault 更新了」还是「镜像被改了」**——两种情况都表现为镜像与 vault 不一致。有了上次同步的基线才能判定，而且校验从此不需要访问 vault。

防误改三层：只读横幅加 `linguist-generated`（GitHub 的 PR diff 默认折叠）、pre-commit、CI。hook 不随 clone 分发，每个克隆要 `git config core.hooksPath .githooks` 一次。

## 读文档

直接读仓库里的镜像，不用访问 vault：内容与 vault 逐字一致，只多了顶部的只读横幅，以及把 `[[wikilink]]` 改写成的相对链接。

## 文档怎么写

**只陈述当前结论，不留变更痕迹。** 不写「原始需求如何如何」「这是对原稿的修正」「原来是 X 现在改成 Y」。理由要说"为什么这样是对的"，不说"为什么不那样"。改动的来龙去脉写进 commit message，那才是它的位置。层叠的历史文档会持续再生假话：「原始记录 + 更正注记 + 对更正的更正」这种结构，每次扫描只覆盖到不同的子集，逐句改永远改不完。

**不用英文直译式术语。** 形状（shape）、扇出（fan-out）、一等公民（first-class citizen）、单一事实源（single source of truth）这类词在中文里没有约定含义，读者要先翻回英文才懂。两条出路：用中文本来就这么说的词，或者直接写英文原词。已经通行的音译/意译词（幂等、快照、编排、契约）不在此列。

**一处定义，他处指向。** 同一条规则不要在两个文档里各写一遍——必然分叉，而分叉之后两份都不可信。项目自己维护一张「哪个主题的唯一出处在哪篇」的表；写一条规则之前先对它，多半已经有地方写了，该做的是指过去。

**引用一律用 Obsidian 原生写法。** vault 里只写 `[[目标]]`、`[[目标|别名]]`、`[[目标#小节]]`，不手写 `[文本](路径.md)`。原生写法在 Obsidian 里重命名文件会自动跟着改，也进反向链接；手写的 Markdown 链接重命名之后就是死链，而且它落在所有检查之外——同步只自查自己生成的那批链接，手写的既不进账目也没人验。镜像侧的相对链接由同步生成，所以同一份写法两边都点得动，不必手工维护两套。

各形态落到镜像里是这样：

| vault 里写 | 镜像里 |
|---|---|
| `[[目标]]`、`[[目标\|别名]]` | 相对链接。表格单元格里的分隔符要写 `\|`，裸竖线会把单元格切开 |
| `[[目标#小节]]` | 相对链接带锚点，点过去落在那一节 |
| `[[目标#^块号]]`、对不上任何标题的锚点 | 相对链接，落在文件顶部。同步输出会逐条列出来 |
| `![[目标]]` | 原样保留，GitHub 上点不动 |
| 目标不在镜像里 | 原样保留 `[[...]]`，一眼看得出这是 vault 内部笔记 |

锚点是按目标文件的标题算出来的：同步时读那篇的标题，按 GitHub 给标题生成锚点的规则转换（转小写、删标点、空格换连字符）。所以**标题改了字，指向它的锚点会跟着算对，不用手工维护**；但目标那一节被删掉时锚点译不出来，同步会把它列进「锚点译不出来」那一栏——看到就去改。

指向别篇的小节写 `[[文档#小节]]`，不要写「见某篇第三节」：前者跟着标题走，后者在章节增删时会静默指错。同篇内不得不用章节号时，改动后逐个核。

## 改文档

只在 vault 里改。vault 位置在 `.mirror.conf.local` 的 `MIRROR_VAULT_ROOT`（同名环境变量可临时覆盖）；没有这份文件时 `sync-docs.sh` 会报出来并给出该写什么。多人协作怎么摆见 `安装.md`——**各自复制一份 vault 会互删**。改完跑：

```bash
./scripts/sync-docs.sh              # 同步并重写基线
./scripts/check-docs-mirror.sh      # 退出码 0 才算镜像干净
cd <镜像目录> && shasum -a 256 -c ../<镜像名>.manifest | grep -v ': OK$'   # 应无输出
```

改动碰到 mermaid 代码块时另外解析一遍再提交（`mermaid.parse`，GitHub 用 11.x）。图渲染失败在 GitHub 上是一个红框，本地看不出来。没碰到 mermaid 就不跑这步，也不要声称跑了。

基线文件要跟镜像在同一个提交里——漏了它，别人和 CI 跑校验会报「内容被修改」。

### 这三条命令查不出源里少了东西

基线由同一次同步重写，而校验只比对镜像与基线。所以 vault 里删掉或漏掉的文件会被 `rsync --delete` 从镜像里清掉，同时三条命令**全绿**——删除对它们不可见。

`sync-docs.sh` 末尾会打一遍 `git status --short`。**读它，出现 `D` 就停下来问**，不要连着提交。已经这样险些丢过一次：图统一改走 mermaid 之后 vault 侧删掉了整个 `图/`，镜像里那 20 个文件就等着被下一次「只改一句话」的同步顺手带走。

### 同步中断时的假警报

wikilink 改写失败会让同步停在半成品状态：镜像已更新、基线还没写。此时校验会把**所有**文件报成「内容被修改」。那是中断状态的表象，不是有人手改了镜像——修好报错的原因重跑同步即可。脚本自己打了这句话，但只看退出码的人会误判成一场事故。

### 镜像被就地改了

`sync-docs.sh` 覆盖前会内容级比对基线，把手改过的文件备份到 `.<镜像名>-手改备份-<时间戳>/` 并在输出里列出，不会静默丢弃。改动有价值就搬回 vault 再同步；是误改就 `git checkout -- <镜像目录> <基线文件>`。

## 批注式评审

用户在 Obsidian 里就地批注：把相关标题或句子 `==高亮==`，挂一个脚注 `[^n]: 要改成什么`。

**找批注要扫标记，不要 diff vault 与镜像。** 镜像的 wikilink 已被改写、顶部还多了横幅，于是每个文件都有差异，批注会被噪音整个盖住。扫 vault 侧的 `==...==` 与 `[^n]:`，用 Python 扫——`grep` 在很多机器上是别的实现的 alias（ugrep 之类），数中文行不可信。

四步：

1. 扫出全部批注；
2. 落成正式条文，**清掉高亮标记与脚注本身**，包括正文里的 `[^n]` 引用——批注是交互媒介，不是文档内容。清完复扫一遍，确认剩 0；
3. 处理它牵动的其他文档（下面那张表）；
4. 同步、提交，并说明替用户做了哪些判断。

### 一句话的批注牵动哪些地方

| 批注要求的东西 | 还要落到哪 |
|---|---|
| 上限、数量、超限怎么办 | 项目放规则检查清单的那篇——**上限没有检查项就等于没有上限**；以及里程碑或计划里的实现清单，否则实现时会漏掉 |
| 随实测更新的能力数值 | 配置数据那一侧（模型能力档之类），文档只留机制与评估维度。反过来也成立：**自己定的纪律不进配置**——配置放的是外部声明的事实、随实测变，而纪律要的正是它不变 |
| 一条新规则 | 先对唯一出处表，在已有的那一处写，别开第二处 |
| 章节的增删 | 带章节号的引用（`第三节`、`3.2`）逐个核，它们会静默指错 |

## 沉淀

开工前读一遍项目的工程经验与遗留清单。收尾时按这个顺序：

**一、先跑 CI 跑的那一串，命令从 workflow 文件里抄，不凭记忆列。** 漏掉的那条几乎总是格式门禁——它不让任何测试变红，所以本地测试全绿而 CI 是红的。

**二、把这一轮返工过、评审挑出来、走了弯路才找对的地方逐个问「换个题目还会不会再踩」**，然后按落点分：

| 是什么 | 落到哪 |
|---|---|
| 能变成测试的 | 补成测试，别留在清单里。清单要靠人记得，测试每次都替你记得 |
| 这个代码库特有的待办，或已判定「不是问题」的 | 遗留清单。条目要自足：涉及哪些文件、判断依据、正解是什么 |
| 换个项目也成立的方法 | 工程经验。再问它挑不挑领域：挑就进那一层，不挑进通则，**两头都放必然分叉** |
| 照原样重跑会重现这一轮修掉的缺陷的代码块 | 回头改实施计划——计划是要能再跑一遍的东西 |

**三、写之前先扫要落的那一节。** 多半已经有一条讲的是同一件事的另一个侧面，**合并比追加好**；被更普适的条目盖住的旧条目当场删掉。

**四、别在两处抄同一份名单。** 要清的东西如果计划里已经列了，清单条目就指过去，只留「这些不会自己变红」这类无法自动化的判断。两份名单必然先分叉，分叉之后两份都不可信。

## 改这套脚本之前

**变量后面紧跟中文标点要写成 `${VAR}`。** macOS 自带的 bash 3.2 把 ≥0x80 的字节当作合法的标识符字符，所以 `$MIRROR_MANIFEST（21 个文件）` 里的变量名会连着中文括号一起被解析，在 `set -u` 下直接崩。这条踩过：`$relpath（已被删除）` 那条分支从来没被执行过，所以带着这个缺陷活了很久。

**改完必须做回归：跑一次同步，镜像与基线要逐字不变**（`git status` 无输出）。这是唯一能证明改写没有悄悄改变产出的办法——横幅少一个换行、rsync 少收一类文件，都会让全仓库的哈希变一遍，而所有校验照样全绿。

## 红旗

- 在镜像目录里就地改，想着「改完再搬回 vault」——改动不会回流，pre-commit 会拒，而没装 hook 时它会一路进 PR
- 只看 `check-docs-mirror.sh` 的退出码就认为同步没问题——它有两种全绿的假象，见上面两节
- 声称跑了 `mermaid.parse` 或 `shasum -c` 而实际没跑
- 用 `grep` 数中文行，然后相信那个数
- 凭记忆列本地验收命令，而不是从 CI 的 workflow 抄
- 新装一条检查却没证明它会失败——不会失败的检查比没有检查更糟，它稳定地报告成功
